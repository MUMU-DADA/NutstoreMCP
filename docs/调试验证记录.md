### 两个真实产品缺陷（由受限环境暴露）

1. **传输层异常穿透。** `HttpClient` 抛的 `HttpRequestException` / `TaskCanceledException` 从 `WebDavClient.SendAsync` 直接穿出去，而调用方只 catch `NutstoreException`。`--doctor` 因此整段自检崩在未处理异常上，MCP 工具层也只剩一句通用错误。新增 `NetworkException`（`NETWORK_ERROR`）在发请求处一次性翻译 —— 网络问题和「服务端拒绝」必须分得开，前者没有状态码可看。
2. **测试管道死锁。** `McpEndToEndTests` 只读 stdout、让 stderr 攒在管道里；子进程把 stderr 缓冲区写满就阻塞在写上，父进程却在等 stdout 关闭。`--doctor` 崩溃时那段堆栈正好超过管道缓冲，测试挂到超时而不是干脆失败。改为两个流并发读，并把 stderr 带进断言消息。

### 验证脚本改造

`verify.ps1` 原先在受限文件沙箱里的表现是「构建失败 / 0 个警告 0 个错误」，看不出原因。逐条定位后改了四处：

- 逐项目 `--no-restore` 构建，取代解决方案级 `dotnet build`。解决方案构建会先跑 Restore，受限环境里 HTTPS 不通就只回一句「0 个错误」。缺 assets 时单独报「这一步需要联网」，不冒充构建失败。
- 主测试与探针都带超时。此前有测试挂起时整轮验证永远停在那里，既拿不到摘要也不知道是谁挂的。
- 探针判定改解析它自己打印的结论行，不再依赖 `Process.ExitCode`（受限环境里打不开子进程句柄，该值返回空）。
- 探针暂存目录与配置自测临时目录探测可写性，不可写时退回系统临时目录。

受限文件沙箱里实测到的限制（都会伪装成「代码坏了」）：HTTPS 完全不可用（Schannel 0x8009030E）；MSBuild 并行节点之间的命名管道被挡，`recon/UiHookProbe` 需要 `-m:1`；`Process.ExitCode` 不可读；`%LOCALAPPDATA%` 不可写；`File.Replace` 被拒绝（配置补丁自测因此必须沙箱外跑）。

## 十二、B2/C3 受限范围：纯数字名称

上一轮已证明大小写别名会被服务端接受、再由客户端做冲突改名，而只读反编译显示改名分支在别的内容组合下可能移动甚至删除既有对象。本轮验证「结构上消除别名」这条路能不能走：**工具生成的纯 ASCII 数字目录名 + 纯 ASCII 数字文件名、无扩展名**。大小写折叠对数字完全无效，所以别名不是被降低概率，而是不可能出现。

### 由此确定的设计（待实现）

受限创建工具的**结构保证是「父目录由本调用新建且已确认为空」**，而不是名字长什么样：

1. 目录名与文件名由调用方给出，但必须是单个路径段（无 `/`、`\`、遍历、非法字符）；
2. 建目录前只读确认沙箱根下不存在同名或大小写别名；
3. 建目录后只读确认该目录为空 —— 新目录里没有任何既有对象，其后创建的文件因此不可能与任何对象构成别名（这一条是全部安全性的来源）；
4. 上传内容 → 发布元数据，提交前再确认目标仍不存在；只尝试一次；
5. 提交后核对文件类型/大小/云端 hash/版本、父目录成员唯一、按真实版本下载逐字节比对。

不做：任意路径、覆盖已有对象、递归创建、重试、回滚、删除。命名范围优先纯数字；若要放宽到普通名字，第 3 条必须保留。

证据支持：上一轮在新建目录里用普通名字两次创建均成功且无冲突（别名风险只在**对已存在对象**创建别名时出现），本轮用纯数字在纯数字目录里再次端到端验证通过。

### 第一次上线失败暴露的两个问题

1. **默认域读错了上传返回值。** 上传入口 `c6e98b16ca15` 的**声明返回类型是 `string`**（客户端内部已经解析 `ObjectNameResponse.name`），而交接文档写的是「读 `ObjectNameResponse.name`」，按后者写成读对象成员就必然失败。桥实验里 `Slot` 直接把字符串当值返回，把这个差异藏住了 —— 教训是**接默认域钩子前必须核对反编译签名**，不能只信文档里的描述。已按 `string` 修正。
2. **`Execute` 没有清空上一次的结果。** 受限创建连着调两次（建目录、建文件），第二次失败时会继承第一次的 `ok` / `verified` 而误报 `executed=true`。这个 bug 是新增的 32 项离线守卫用例抓出来的（`写入抛异常后仍复查且不自动重试`）。已在每次 `Execute` 前重置 `Result`、`HookOk`、`HookVerified`、`HookVerification`。

第一次失败时**内容已经上传、元数据从未提交**（`contentUploaded=true`、`metadataAttempted=false`），按既定边界没有回滚、没有删除；未引用内容的服务端保留期仍未确认。这次失败也顺带证明了分阶段报告是有效的：`refusals` 里能直接看到卡在哪一步。

### 变更范围与部署方式

新增契约方法 `IUiHook.CreateCloudFile`，默认域实现只做「全量上传 → 发布元数据 → 写后只读复查」，防覆写判断留在插件的 `CloudWriteOperations.CreateFile`（三重锁、名字段校验、根下别名检查、空目录确认、写后四核对）。工具只接受两个单段名字，不接受多段路径。

**部署经验**：UiHook 程序集是从 `%LOCALAPPDATA%\NutstoreMcp\plugin-<时间戳>\` 加载的，程序目录只装 Bridge 与 Contract。所以契约没变时，改 UiHook 只需 `.\deploy\restart-client.ps1 -SkipInstall` —— **不弹 UAC**。这次就是因为先做了一次带安装的重启（契约已更新），第二次只重启就完成了修复。

离线守卫用例后来补到 **34 项**（主测试合计 355），新增两项对抗形态：写后目录列表读不到（无法推断目标唯一存在）与写后出现仅大小写不同的副本，两者都必须拒绝报告成功。
