### 两个真实产品缺陷（由受限环境暴露）

1. **传输层异常穿透。** `HttpClient` 抛的 `HttpRequestException` / `TaskCanceledException` 从 `WebDavClient.SendAsync` 直接穿出去，而调用方只 catch `NutstoreException`。`--doctor` 因此整段自检崩在未处理异常上，MCP 工具层也只剩一句通用错误。新增 `NetworkException`（`NETWORK_ERROR`）在发请求处一次性翻译 —— 网络问题和「服务端拒绝」必须分得开，前者没有状态码可看。
2. **测试管道死锁。** `McpEndToEndTests` 只读 stdout、让 stderr 攒在管道里；子进程把 stderr 缓冲区写满就阻塞在写上，父进程却在等 stdout 关闭。`--doctor` 崩溃时那段堆栈正好超过管道缓冲，测试挂到超时而不是干脆失败。改为两个流并发读，并把 stderr 带进断言消息。

### 验证脚本改造

### 由此确定的设计（待实现）

受限创建工具的**结构保证是「父目录由本调用新建且已确认为空」**，而不是名字长什么样：

1. 目录名与文件名由调用方给出，但必须是单个路径段（无 `/`、`\`、遍历、非法字符）；
2. 建目录前只读确认沙箱根下不存在同名或大小写别名；
3. 建目录后只读确认该目录为空 —— 新目录里没有任何既有对象，其后创建的文件因此不可能与任何对象构成别名（这一条是全部安全性的来源）；
4. 上传内容 → 发布元数据，提交前再确认目标仍不存在；只尝试一次；
5. 提交后核对文件类型/大小/云端 hash/版本、父目录成员唯一、按真实版本下载逐字节比对。

不做：任意路径、覆盖已有对象、递归创建、重试、回滚、删除。命名范围优先纯数字；若要放宽到普通名字，第 3 条必须保留。

证据支持：上一轮在新建目录里用普通名字两次创建均成功且无冲突（别名风险只在**对已存在对象**创建别名时出现），本轮用纯数字在纯数字目录里再次端到端验证通过。

## 十七、设置页开关重启后消失：根因与自愈

用户报告「UI 上面的 MCP 开关没了」。实测确认：`nutstore_ui_find` 查 `MCP` 只命中同步文件夹名 `mcp-test`，设置页里确实没有开关。

**根因不是崩溃**：开关是**运行时插进设置页的 WPF 元素**，不写配置、不进 XAML，只由 `nutstore_ui_install_toggle`（或插件启动流程）注入。客户端在 **2026-10-16 00:19 重启过**，之后没有任何代码再调用注入 —— 于是开关就消失了。这也是设计缺陷：界面上没有任何地方能把它找回来。

**修复**（插件侧，可热重载，无需重启客户端）：UI 钩子接入后（`PluginEntry.AttachUi`）启动一个后台注入线程 ——

- 前 2 分钟每 2 秒试一次，覆盖正常启动（此时设置页可能还没实例化，`AddToggle` 会返回「没找到设置项容器」）
- 之后每 15 秒试一次直到成功，覆盖「用户很久以后才第一次打开设置页」
- 成功即停；连续 5 次异常才放弃（客户端退出时跨域代理会抛 `RemotingException`，偶发失败不该永久失去自愈能力）
- MCP 服务当前关着时也照装 —— 那种情况下用户恰恰需要它来重新打开

标题与说明文字提成 `PluginEntry.ToggleTitle/ToggleSubtitle`，自动恢复与 `nutstore_ui_install_toggle` 共用，避免两处漂移。

**验证**：

| 场景 | 证据 |
|---|---|
| 热重载后 | 日志 `设置页开关已自动恢复（第 1 次尝试）`（09:39:02，钩子接入后约 2.2 秒） |
| **冷启动（真正要证明的）** | 重启客户端 → PID 83700；09:40:04 钩子接入，**09:40:06** 自动恢复；`nutstore_ui_find` 查到「MCP 服务器」控件。全程**没有手动调用任何工具** |
| 回归 | `verify.ps1` 全绿 |

顺带一条经验：这类「运行时注入、不落盘」的状态天然不跨重启，凡是靠 UI 注入的能力都要自带自愈，否则用户看到的就是「东西凭空消失」。
## 十八、按本地文件创建云端文件（读取白名单，默认关闭）

受限创建原来只收 base64，实际很难用。现在 `nutstore_l3_create_file` 增加 `sourcePath`：
直接给本地文件路径，内容在**真正执行那一步**才读，**预演不读内容**。

### 为什么需要一个白名单，且默认关闭

让调用方传本地路径去读，等于给了「读本机任意文件」的能力 —— 一个被诱导的助手可以把
`.ssh` 或凭据文件读出来传到云端。写入还有令牌挡着，读取却只受调用方自觉约束，这不能接受。
所以：

- 白名单文件 `%LOCALAPPDATA%\NutstoreMcp\read-roots.txt`，一行一个**绝对路径**，`#` 开头为注释
- **文件不存在或没有有效条目时，本地文件模式直接不可用**（fail-closed），只能用 `contentBase64`
- 读不到白名单文件也按「未启用」处理 —— 失败朝更严格的方向倒

### 校验了什么

| 检查 | 理由 |
|---|---|
| 绝对路径 + `Path.GetFullPath` | 相对路径会跟着当前目录漂，范围不可控 |
| 必须落在白名单根之下，**按目录边界比较** | 纯字符串前缀会让 `C:\data-evil` 混进 `C:\data` |
| 存在、不是目录 | `FileInfo.Exists` 对目录也返回 false，必须先 `GetAttributes` 再判 |
| 不是符号链接/目录联接（`ReparsePoint`） | 否则读出来的是白名单外的内容 |
| 1 字节 ~ 256 KiB | 空文件走另一条上传分支（当前不支持）；上限与内联模式一致 |
| 读取时复核长度 | 校验与读取之间文件被改动就中止，绝不传未知大小的内容 |

### 在线验证

脚本 `.test-tmp/create-from-file-online.ps1`，报告 `.test-tmp/create-from-file-eeeae7d1-report.json`：

| 场景 | 结果 |
|---|---|
| 白名单文件不存在 | `ok=false`「本地文件模式未启用…」，**策略层就拒绝，不进守卫、不读绑定、不碰云端** |
| 白名单外（`C:\Windows\win.ini`） | `ok=false`「不在读取白名单内」 |
| 同时给 `sourcePath` 与 `contentBase64` | `ok=false`「必须且只能给一个」 |
| 预演（白名单内） | `allowed=true`、不执行；`probe.contentSource=file:…`、`contentBytes=191`（与本地一致） |
| 真创建 | `executed=true`，写后四核对通过；云端版本 1、hash 与本次上传一致 |
| 只读复核 | 云端大小 191 字节，**下载后与本地文件逐字节一致** |
| 收尾 | 令牌归零、白名单删除（恢复默认关闭） |

成品对象：`/file-eeeae7d1/payload-eeeae7d1.txt`（191 字节，版本 1）。

### 已知限制

- 上限仍是 256 KiB：更大的文件要走客户端的**分块上传**（`MakeStoreDeltaObjectRequest` + 块列表），
  那条路径与云端 hash 的多块公式都还没验证，需要单独的写实验并会消耗上传流量。
- 只挡了文件自身的 `ReparsePoint`；路径中间的目录联接仍是理论缺口，白名单本身是用户可控的可信目录，暂按可接受处理。
