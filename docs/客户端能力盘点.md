## 我的建议顺序

1. **A1 云端搜索 + A2 容量用量** —— 只读、高价值、零风险，可以立刻做
2. **A4 文件历史版本列表** —— 只读，且是「恢复版本」的前置（先能看才能谈恢复）
3. **B1 下载文件内容** —— 只读，能做绑定做不到的事
4. **C1 移动/重命名** —— 第一个写操作，需要新守卫设计
5. 其余按需

**不建议做 C6（删除）**：收益小、风险极高，且与「绝不导致数据丢失」的约束冲突。

## 一个结构性提醒

现在每加一个客户端能力都要改 UI 钩子 → **必须重启客户端**（默认域的程序集卸不掉）。
这一轮为了验证两个设置方法，重启脚本跑了三次。

如果后面要连着做 A1/A2/A4/B1，值得先花一次重启把钩子改成**按能力 ID 分发的稳定接口**：
新能力只改插件侧，不再动钩子。代价是钩子从「几个明确方法」变成「一个通用分发器」，
需要配套的白名单守卫 —— 这是个权衡，不是纯粹的改进。
