# 跨端兼容性评估（2026-10-18）

目的：把坚果云 **macOS / Linux / Android / iOS / Web** 客户端拉下来，判断现有「进程内调用客户端自身实现」的 MCP 路线能否复制到其他端，以及代价。
本文只写**可复现的观测**；未验证的部分集中列在最后一节，不要当成结论引用。

## 结论摘要

| 端 | 客户端技术栈（实测） | 现有 .NET 插件能否复用 | 进程内插件路线可行性 | 难度 |
|---|---|---|---|---|
| Windows | .NET/WPF，**7.2.12.0**（现状） | — | 已实现（36 工具） | 基线 |
| macOS | **Java/SWT**（JavaBE 外壳 + 捆绑 jlink JRE 21），**6.4.8** | 否，需用 Java 重写 | 可行，但签名/Gatekeeper 摩擦大 | 高 |
| Linux | **Java/SWT**（jlink JRE + Python GTK 托盘），**6.4.3** | 否，需用 Java 重写 | **可行，摩擦最小** | 中高 |
| Android | Kotlin/Java（Room + OkHttp + X5 WebView），**4.26.7** | 否 | 否（无 root 不能注入；MCP 无落点） | 极高，不建议 |
| iOS | 原生 App（bundle `com.jianguopuzi.ios`），**5.6.26** | 否 | 否（沙箱 + 商店签名） | 极高，不建议 |
| Web | 网页端（官网页脚 **4.23.1**） | 否 | 只能走 Cookie/AJAX，能力子集 | 中（只读） |

一句话：**桌面端存在两套互不相同的实现**——Windows 是 .NET，mac/Linux 是同一套 Java 核心。MCP 想上 mac/Linux，本质是把插件**用 Java 重写一遍**（进程内注入仍可行，且 Linux 上注入很便宜），而不是移植现有代码；移动端与插件路线不兼容。

## 二、各端实测技术栈

### macOS：Java（JavaBE）+ 原生 File Provider 扩展

`Nutstore.app/Contents/Info.plist` 直接给出事实：

- `CFBundleIdentifier = net.nutstore.NutstoreJavaBE`
- `JVMMainClassName = nutstore.client.gui.NutstoreGUI`
- `JVMRuntime = jdk-fx.jdk`，`JVMOptions` 含 `-XstartOnFirstThread`、`--add-modules=jdk.httpserver`、`-Dnutstore.config.dir=$APP_ROOT/Contents/Resources/conf`
- `Contents/Java/nutstore_client-6.4.8.jar`（26,062,933 B）+ `Contents/PlugIns/jdk-fx.jdk`
- 捆绑运行时是 **jlink 裁剪的 JRE 21.0.6**（`Contents/Home` 只有 `conf/legal/lib/release`，**没有 `bin/java`**），模块表含 `jdk.httpserver`，**不含 `jdk.attach`**
- 启动器 `Contents/MacOS/Nutstore` 是经典 JavaAppLauncher，字符串里有 `JVMOptions` / `JVMArguments` / `JVMMainClassName`
- `Contents/NutstoreFilesD.app` 是**原生 File Provider 扩展**（`net.nutstore.osxapp`，6.4.8，含 `.nslnk`/`.nssyncsc` 等 UTI）
- `Resources/conf/nutstore.properties`：`appserver=app.jianguoyun.com`，`version=6.4.8`

macOS 安装器本身是原生 ObjC（Xcode 16.4 构建，`NutstoreOnlineInstaller`），`Resources/url.conf` 指向真实载荷 zip；`Resources/install_root_ca.sh` 会往**系统钥匙串**安装 USERTrust RSA 根证书（自动化装客户端时要意识到这是持久系统改动）。

### Linux：Java（SWT）+ Python 托盘 + WebUI

- `lib/nutstore_client-6.4.3.jar`（25,115,596 B），MANIFEST：`Implementation-Version: 6.4.3`、`Build-Date: 2025-08-22`、`Build-Commit: b1fda57`
- `jre/` 是 jlink JRE 21.0.6，`bin/` 只有 `keytool` 和 `nutstore`（启动器，ELF）
- `bin/nutstore-pydaemon.py` 明确写出启动命令：`jre/bin/nutstore -ea -client --enable-preview -Dnutstore.config.dir=... -cp lib/... nutstore.client.gui.NutstoreGUI`
- `conf/nutstore.properties`：`appserver=app.jianguoyun.com`、`version=6.4.3`
- `webui/` 是 React 打包产物（4 个窗口），走 SWT Browser 内嵌
- 托盘 `bin/*.py` 用 GTK/AppIndicator，通过 **localhost:19080** 的行协议向 Java 进程发命令（见第四节）

### Windows

现状：`C:\Program Files\Nutstore\bin-7.2.12`（NutstoreClient.exe + NutstoreClient.Legacy.dll 等），插件基线见 [客户端绑定登记](../src/NutstoreMcp.ClientBindings/README.md)。在线安装器只有 3 MB，说明它也是下载器而非完整包。

### Android：Kotlin/Java App，REST `/cmd/*` + `/mcmd/*`

APK 结构：`classes.dex`×3、`lib/arm64-v8a/{libBugly_Native,libEncryptorP,libmupdf_java}.so`、TBS X5 WebView 组件、Room（`obj_metadata`/`trans_task`/`sandbox` 表）、OkHttp/Retrofit（`NutstoreApi`）。

### iOS / Web

iOS：只有元数据（原生 App，最低 iOS 15）。Web：官网页脚版本 4.23.1，未抓包。

## 三、跨端协议与能力面比对

### 3.1 业务契约高度一致（Java 桌面端 vs Windows .NET 端）

Java jar 的类常量里能直接读到与现有插件**同名同义的模型**：

- 写：`CreateFileParam`、`ModifyFileParam`、`WriteObjectMetaRequestEntity`、`CheckBlockOrBlockListRequestEntity`
- 读：`SandboxInfoBean`、`SyncFolderDetailBean`、`SubPathAcl`、`SimplifiedPathAclBean`、`PathPermsList`、`UserInfoBean`、`MeterInfoBean`、`ContactBean`、`TeamGroupsBean`、`EtpConfBean`、`SearchResponse`、`LatestEventId`、`ServerLockResult`
- 分享/链接：`WebPubObjectBean`、`CreateShortcutBean`、`OfficeEditLinkBean`、`CopyResponseBean`
- 内容：`DownloadFileResult`、`GetRange`、`MeterInputStream`、`ObjectNameResponse`
- 上传字段：`fullObjectNameBase64`、`blockListNameBase64`、`hashBase64`、`compressible`、`exAttr`
- 哈希：`getServerSHA256HashBase64`、`getServerSize`、`nutstore/isal/crypto/sha256/SimdBlockListCalculator` + `libnutstore_isal_crypto.so`（ISA-L 加速的块列表计算）

也就是说：**4 MiB 分块 + 块记录/文件记录那套上传算法，在 Java 端也存在**，与 ARCHITECTURE 里记录的 Windows 实现语义一致；`CreateFileParam`/`ModifyFileParam` 的字段布局同样一致。

### 3.2 传输层不同，且 Java 端更"藏"

- Java HTTP 层用 `java.net.HttpURLConnection`，请求头：`Authorization`、`X-Client-Signature`、`x-latest-event`、`x-more-data`、`Content-Encoding`、`Accept-Language`、`User-Agent`
- 签名工具类 `nutstore/client/helper/cd` 使用 **HmacSHA256**（配合 `X-Client-Signature`）→ 外部"重放协议"需要复刻签名，不适合作为移植路线
- **jar 里没有 `/cmd/` 字面量**，也没有 `getEvents*` 字面量（后者只在捆绑的 growthbook/sentry 里出现）；端点路径应是运行时拼接/服务端下发，未定位（见第七节）
- 主机：`appserver=app.jianguoyun.com`、`webserver=www.jianguoyun.com`；`Ik`/`EpServerInfo` 负责多端点探测
- 本地库：jar 字符串里有 `nutstore.db`、`event.db`（与 Windows 的 `%APPDATA%\Nutstore\db1\nutstore.db` 命名一致，路径未验证）

Android 端则把接口名写得很直白：DEX 中共 **36 个 `/cmd/*` + 29 个 `/mcmd/*`** 字面量，例如
`createSandboxV1`、`getSandboxDetailV1`、`getSandboxPathPerms`、`browseVersionsV1`、`restoreFilesV1`、`storeBlockV1`、`storeBlockListV1`、`checkBlockV1`、`checkBlockListV1`、`getLatestEventIdV1`、`getEventsV4`、`getMetering`、`getUserInfoV3`、`pubObjectV1`、`getPubObjectV2`、`writeObjectMetaV1`、`submitCopyV1`、`createShortcutV1`、`deleteSandboxV1`；移动端另有 `loginV2`、`getDirV1`、`getFile`、`uploadFile`、`mkdir`、`moveProgressV1`、`deleteDirV1` 等。
这反过来验证了 Windows 插件里那批 `/cmd/*` 端点的命名规律，也说明 **REST 命令面是 Windows/Android 共用的**。

### 3.3 桌面 Java 端还有两处可用的本地集成面

1. **本地命令套接字（Linux 实测于 Python 侧）**：`network_util.py` 定义 `JAVA_SERVER_PORT = 19080`，协议是 `localhost:19080` 发 `命令\n done\n`，命令集：`open_main_window`、`open_website`、`open_invite_friends`、`pause_sync`、`open_preference`、`switch_account`、`user_guide`、`pack_log`、`exit_client`、`is_paused`、`open_file_in_lightapp`、`open_wizard_in_lightapp`。配置项 `internal.command.handler.enabled` 控制该通道。**只有 UI 类命令，没有文件操作。**
2. **File Provider gRPC（mac 主线）**：jar 内含完整 protobuf/gRPC 定义——`ItemService`、`ShellService`、`Enumerator`、`FileProviderService`，方法含 `Service/CreateItem`、`DeleteItem`、`RenameOrMoveItem`、`FetchData`、`ListDir`、`ListChanges`、`GetSyncAnchor`、`FetchThumbnails`、`ModifyContent`、`ModifyMetadata` 等，走 `com.etsy.net.UnixDomainSocket*` 的 unix socket，目录由 `file_provider_domain_dir` 配置。**这是"外部进程 + 文件面能力"唯一现成的通道**（schema 在 jar 里可读），但只覆盖文件操作，不含同步文件夹/设置/事件。

## 四、按端的兼容难度与路线

前提：现有插件的价值在**语义与安全模型**（三重锁、禁止清单、写后复查、结构安全），这些可以照搬思路；**.NET 代码不能复用**。

### Linux — 中高，建议作为第一站

- 注入面最便宜：启动器 `jre/bin/nutstore` 是 java 启动器，字符串含 `JDK_JAVA_OPTIONS`/`_JAVA_OPTIONS` → **推断 `JDK_JAVA_OPTIONS="-javaagent:agent.jar"` 即可挂载**（未实测）；也可以直接改 `nutstore-pydaemon.py`（它本来就负责拼 `-cp ... NutstoreGUI` 命令行）加一个 `-javaagent`。
- 无签名/商店限制，出问题不影响系统。
- 主要工作量在 **Java 侧重新定位被 ProGuard 混淆的绑定**（12,186 个 class，单字母包名 `a/b/d/f/g/i/k/...`；Windows 侧是 25 个方法/84 项绑定，Java 侧要重做一遍等价物），以及把 36 个工具在 Java 里重写（MCP Java SDK 有官方实现）。
- 版本基线独立：Linux 6.4.3（2025-08-22）与 mac 6.4.8 不同，绑定需要各自基线。

### macOS — 高，Linux 跑通后再做

- 同一套 Java 核心（两版 jar 有 **11,756 个相同路径**，差异是平台适配），理论上代码与绑定可复用。
- 障碍在**怎么挂 agent**：
  - 捆绑 JRE 是 jlink 裁剪版，**没有 `bin/java`，也没有 `jdk.attach`**；
  - 改 `Info.plist` 的 `JVMOptions` 加 `-javaagent` 会**破坏代码签名**，需要 `codesign` 重签 + 处理 Gatekeeper/quarantine；
  - 相对干净的替代：用自备 JDK 21 复刻启动命令（`-XstartOnFirstThread -Dnutstore.config.dir=... -Djava.library.path=Contents/MacOS -cp .../nutstore_client-6.4.8.jar nutstore.client.gui.NutstoreGUI`），不碰原 App；可行性需要真机验证。
- 还要处理与原生 `NutstoreFilesD.app`（File Provider 扩展）的并存，以及 Full Disk Access 等 TCC 权限。
- 额外的免注入备选：直接当 gRPC 客户端连 File Provider 的 unix socket（proto 在 jar 里），能把"文件面"做出来，但做不了同步文件夹/设置/事件。

### Android — 极高，不建议

- 无法进程内注入（无 root）；MCP 在移动端也没有合理落点。
- 外部进程要调用就得拿账号会话，等于冒充客户端（风控/条款风险），而且移动端是 `/mcmd/*` 子集，能力面比桌面窄。
- 唯一"技术可行"的形态是做一个独立 Android App 在系统内复用登录态——与现有项目的安全前提冲突。

### iOS — 极高，不建议

- 原生 App、沙箱、App Store 签名；没有可用的进程内/进程间入口。IPA 本身也没拿到（加密包）。

### Web — 中，但只能算另一条产品线

- 浏览器 Cookie + AJAX 打网页端接口（此前已探到 `/d/ajax/*` 只有账号设置类能力；`/cmd/*` 是否接受网页会话未验证）。
- 风险：CSRF、`X-Client-Signature`、风控、能力子集；安全模型与"用客户端自己的会话"不同，应作为独立的只读适配器评估，不并入本插件。

## 五、建议顺序

1. **Linux Java agent 版**（先只读工具 + 一个受限写工具跑通闭环，再批量搬 36 个工具语义）。
2. **macOS 同源复用**：先用自备 JDK 启动验证，再决定是否走重签路线。
3. 若 mac 卡在签名，退一步评估 **File Provider gRPC 桥**（只覆盖文件面，免注入）。
4. Android/iOS 不做；Web 单独立项、只读优先。

粗估（仅供排期，含逆向定位与联调，不含长期维护）：Linux 2–4 周；macOS 3–6 周（其中签名/启动方式 2–4 天）；Web 只读 1–2 周。

## 六、风险与未知（不要当结论用）

- **没有 mac/Linux 真机**：以上可行性是静态证据推断，未实际启动客户端。
- Java 端**云端端点路径未定位**：jar 里无 `/cmd/` 字面量，端点疑似运行时拼接或服务端下发；如果将来想走"协议级"而不是进程内，需要额外逆向 `X-Client-Signature` 与端点发现逻辑（高风险、随版本失效）。
- **19080 监听端实现未定位**：只在 Python 侧找到端口与命令，Java 侧对应实现未找到（可能由原生/其他机制承载）。
- 自备 JDK 启动 mac 客户端时，SWT/native 库加载与 `-XstartOnFirstThread` 行为未验证。
- iOS IPA 未获取、Web 未抓包。
- 移动端与 Web 的账号/会话凭据处理涉及条款与风控，不做技术可行性之外的判断。

## 附录：复现要点

产物建议落在仓库外的临时目录（如 `$env:TEMP\nutstore-recon`），分析完直接删除；下面是本次的关键步骤，不依赖任何保留的脚本。

```text
1) 下载：地址见第一节表格。用 Node fetch（curl/Invoke-WebRequest 在沙箱下会因 Schannel SEC_E_NO_CREDENTIALS 失败），
   例：node -e "fetch(u).then(r=>r.arrayBuffer()).then(b=>fs.writeFileSync(p,Buffer.from(b)))"
   - macOS 真实载荷地址在 DMG 里安装器 App 的 Resources/url.conf
   - Android 直链来自 d.apkpure.net/b/APK/nutstore.android（302 → data.winudf.com）

2) 解包
   tar -xzf nutstore_linux_dist_x86_64.tar.gz -C <tmp>/linux        # Linux 发行包
   7z x nutstore_client-osx-onlineinstall.zip -o<tmp>/mac            # 需完整版 7-Zip（7z*-extra 里的 7za 不支持 DMG）
   7z x NutstoreOSXInstaller.dmg -o<tmp>/osx                         # 在线安装器 App（原生）
   jar = zip：解压后即可读 META-INF/MANIFEST.MF、conf/、proto 生成的 class

3) 静态检查（本次用一次性 Node 脚本完成，未保留）
   - DEX：解析 zip 中央目录取 classes*.dex，按 DEX 头 string_ids/string_data 读字符串表 → /cmd/*、/mcmd/*、X-Client-Signature
   - Java class：解析 class 常量池（tag 1 = UTF8）导出字符串；nutstore/client 包 12,186 个 class
   - 结构检索：在 class 常量里找 com/sun/net/httpserver、HmacSHA256、X-Client-Signature、UnixDomainSocket、
     file_provider_domain_dir、nutstore.db 等关键词
```

相关：现有架构与安全模型见 [ARCHITECTURE](../ARCHITECTURE.md)，Windows 客户端绑定基线见 [ClientBindings](../src/NutstoreMcp.ClientBindings/README.md)，历史客户端能力盘点见 [归档](archive/2026-10-18-客户端能力盘点.md)。
