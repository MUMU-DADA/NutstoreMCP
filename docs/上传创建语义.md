# 上传与创建文件语义

全新文件需要先上传完整内容，再创建文件元数据。内容上传返回对象标识，不代表文件已经创建。本轮完成反编译研究、哈希公式验证和受限桥的离线保护验证，B2/C3 尚未接入专用工具，也未执行联合上传创建或碰撞实验。

## 客户端入口与参数

以下方法均属于 `A.c3795a089d76f103f11c4fe70f38ac8ca`（下文称 CloudOps），使用客户端自己的请求和会话链路。

| 用途 | 完整方法名与签名 | 结论 |
|---|---|---|
| 全量内容上传 | `c6e98b16ca153095711ef04f770d2ca53(SandboxIdentifier, Stream, long size, long bytesInStream, CompressionMethod, string urlSafeBase64Md5Sum)` | 全新文件应使用此入口；上传请求没有目标路径，返回内容对象标识 |
| 增量内容上传 | `cd20b0bb262184cd692f5b3bba1477f24(NutstorePath, long basisVersion, Stream, long size, long bytesInStream, CompressionMethod, string urlSafeBase64Md5Sum)` | 原盘点 B2 实际为增量入口，不能用于全新目标 |
| 创建文件元数据 | `cf02e04aba958d38757ce778e8f94ae50(CreateFileParam)` | 将目标路径、内容标识、大小及云端 hash 发布为文件 |

全量入口调用 `NutstoreRequest.MakeStoreFullObjectRequest`；增量入口调用 `MakeStoreDeltaObjectRequest`。内容响应必须为 HTTP OK，然后读取 `ObjectNameResponse.name`。这个标识原样填入创建参数，不自行变换编码。

`NutstoreClient.Helpers.CreateFileParam` 是 struct，完整字段如下：

| 字段 | 全新普通文件的用法 |
|---|---|
| `path` | 由同一 NSSandbox 构造的规范目标 NutstorePath，不能是根 |
| `size` | 原始文件字节数 |
| `hashBase64` | 下节的客户端云端 hash，不能直接用文件字节 SHA256 |
| `fullObjectNameBase64` | 全量上传返回的内容对象标识 |
| `blockListNameBase64` | 全量上传方案设为 null |
| `compressible` | 不压缩实验设为 false，符合客户端 NONE 分支 |
| `exAttr` | 普通小文本实验设为 null |

`fullObjectNameBase64` 与 `blockListNameBase64` 必须恰好一个非 null。参数没有 version 或时间戳。创建入口未设置 `WriteMetaDataParams.version`，所以实际请求版本为默认 **0**；返回版本来自服务端响应，不能人为补成提交版本 1。

## 真实调用链与哈希协议

创建处理器 `A.cc29d1c1a8c027ad98117e3ab0536f38b` 先计算客户端文件 hash，调用上传器，再将上传结果的完整内容标识填入 `CreateFileParam.fullObjectNameBase64`，最后调用 CloudOps `cf02...`。上传器对不大于 393216 字节的普通文件选择全量方案；NONE 分支传 `size == bytesInStream`，并设置 `compressible=false`。

证据：[处理器计算 hash，第 118 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:118)、[创建参数及调用，第 86 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:86)、[上传器小文件分流，第 1752 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cbf0c90264986862bea8d3de0314eee3f.cs:1752)、[NONE 全量调用，第 1480 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cbf0c90264986862bea8d3de0314eee3f.cs:1480)。

传输 MD5 与元数据中的云端 hash 是两个不同值：

- 传输 MD5：客户端使用 `StringUtils.BytesToURLSafeBase64String(HashAlgorithms.GetMd5Digest(stream))`。应复用客户端的编码 helper，避免猜测 URL-safe Base64 的 padding 规则。MD5 helper 恢复原流位置，且拒绝空流。
- 云端 hash：按 **4 MiB** 分块；每块计算 `SHA256(block)`，再附上块长度的 **8 字节大端整数**，得到 40 字节记录。对按顺序拼接的记录再计算 SHA256，结果采用普通 Base64。文件总大小仍是各块原始字节数之和。

单块非空小文件公式为：

```text
cloudHash = Base64(SHA256(SHA256(fileBytes) || BE64(fileBytes.Length)))
```

本轮对 B1 下载得到的全新 49 字节测试文件独立计算此公式，结果与真实云端 hash 完全一致。这证明了单块公式，不等同于上传或创建流程已经在线验证。

空文件是特殊分支：客户端云端 hash 为 32 个零字节，并跳过内容上传；创建参数使用 `fullObjectNameBase64=null`、`blockListNameBase64=Base64(40 个零字节)`，不能把两个名称都设 null 或用空字符串代替。首次联合实验应使用非空小文本。

证据：[MD5 实现，第 16 行](%LOCALAPPDATA%\NutstoreMcp/decomp-common/Nutstore.Common.Helpers/HashAlgorithms.cs:16)、[4 MiB 默认块大小，第 152 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cb1c0cd8c8f92157417db8555fbe83329.cs:152)、[块摘要生成，第 171 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cd1b4f8fe19d13693bd66675e0f9edc5f.cs:171)、[40 字节记录，第 48 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cb23ecc4ac6ddcc7512c3ba26c30a6ffb.cs:48)、[组合摘要与空文件，第 155 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cb1c0cd8c8f92157417db8555fbe83329.cs:155)。

## 为什么不调用完整创建处理器

完整 `cc29...` 处理器不仅创建文件：它会自动创建父目录，按相同 hash/大小寻找现有 DAO 对象后移动或复制，还有 FRN 移动分支。这些行为超出“只创建全新目标”。实验应直接调用全量 CloudOps 入口与 `cf02...`，不调用整个 processor。

证据：[自动创建父目录，第 117 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:117)、[FRN 移动，第 465 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:465)、[去重移动，第 540 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:540)、[复制，第 665 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/cc29d1c1a8c027ad98117e3ab0536f38b.cs:665)。

## 碰撞边界与最小安全实验

`cf02...` 本体没有目标查重、`noReplace` 或目标版本条件。正常客户端按本地 DAO 状态分流创建与修改。错误定义包含 `ConcurrentUpdate`、`DuplicateName`，但不能只凭反编译断言创建入口遇到已有目标一定拒绝且保持旧内容/版本不变；**C3 的服务端碰撞行为尚未在线确认**。

证据：[创建/修改分流，第 729 行](%LOCALAPPDATA%\NutstoreMcp/decomp/A/c98050fdd87287a2fff9da0852ab8a97a.cs:729)、[错误码定义，第 37 行](%LOCALAPPDATA%\NutstoreMcp/decomp/NutstoreClient.Connection/RequestException.cs:37)。

首次成功实验的前提及顺序：

1. 只使用本轮新建专用目录下的唯一新文件名。确认父目录存在且为目录；目标详情不存在、忽略大小写列表无碰撞。有 tombstone 也拒绝，以满足全新目标。
2. 准备小于 64 KiB 的非空普通文本。用同一不可变字节快照计算 MD5 和云端 hash，位置 0 的 MemoryStream 以 NONE 上传一次。
3. 收到非空内容标识后，提交元数据前再次只读确认目标仍全新。任何读取错误或状态变化都停止发布，不清理已上传内容。
4. 构造上表的 CreateFileParam，调用 `cf02...` 一次。检查返回目标路径与正版本；读取云端唯一目标，确认普通文件、大小及云端 hash，再用 B1 按真实版本下载并逐字节比较。
5. 只有内容上传、元数据调用和全部复查一致时报告创建成功。工具不主动重试、不回滚、不调用完整 processor，也不删除测试对象。

防覆写保证需要另在本轮创建的一次性哨兵对象上验证：以不同内容尝试相同名字，确认明确拒绝，且哨兵 hash、版本和下载字节都未变化。该实验不能使用用户已有文件，也不能把 C1 移动的 DuplicateName 实测结果当作 C3 已验证。

失败报告按阶段保留 `contentUploaded`、`metadataAttempted`、`metadataSubmitted`、`verification`，并区分“未调用”“调用失败”“结果未知”。异常只输出类型和结构化错误码，不输出原始消息、DetailMsg、Payload 或会话信息。调用异常即使复查形态一致，也不直接归因为本次创建成功；只读结果单独报告。

当前 DLL 的字符串资源静态解码确认创建操作为 `add`，修改为 `edit`，简化字段包装器为 `overwrite`。`version=0` 是创建请求的默认占位，不能解释为服务端 CAS/noReplace 保证。`UpdateMetaDataResult.path` 是输入回显，服务端响应仅提供 version；因此必须复查父目录完整列表，确认没有产生改名副本。精确路径和大小写变体冲突须分别实测。明确 `DuplicateName/ConcurrentUpdate` 且哨兵全部元数据、版本列表和下载字节不变，才支持该场景的拒绝结论。

工具自身不重试；客户端 HTTP 实现可能在 LibCurl TLS 错误后切换 .NET 重发，并写 `ForceDisableLibCurl` 设置。因此一次桥调用不能等同于底层 exactly-once。393216 字节是客户端上传器选路阈值，不是服务器上限；64 KiB 仅为首轮实验范围。长期大文件方案及空文件须另行验证。

桥新增 `BUFFER|base64` 和 `VALUE|CreateFileParam|字段|参数...`：仅新建不超过总计 8 MiB 的只读诊断流与七字段白名单 DTO，禁止已有对象 SET、私有/静态/readonly 字段和反射/委托签名。脚本结束只释放桥自有流；客户端调用异常仅输出异常类型、ErrorCode 和 HTTP 状态。

上传成功而未发布元数据时，仅能确认内容存储阶段完成；未引用内容的服务端保留周期尚未确认。不得为了回滚而调用删除接口。
